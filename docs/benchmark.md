# 잠금 전략 비교 방법

## 실행

Docker Desktop이 실행된 상태에서 프로젝트 폴더의 PowerShell에서 실행합니다.

```powershell
.\run-tests.ps1 -Benchmark
```

다른 환경에서는 `mvn -Dlab.benchmark=true verify`를 사용합니다.
일반 `verify`는 기능 테스트 8개를 실행하며 벤치마크는 명시적으로 활성화할 때만 실행합니다.
전체 벤치마크 제한 시간은 15분입니다. [2026-10-21 측정 결과](benchmark-results-2026-10-21.md)를 기록했습니다.

## 동일하게 유지하는 조건

- 같은 MySQL 컨테이너, READ COMMITTED, 커넥션 풀 최대 16
- 동시 실행 스레드: 8 / 16
- 시나리오: 각 요청이 서로 다른 계정 사용 / 모든 요청이 같은 계정 사용
- 비교 방식: OPTIMISTIC / PESSIMISTIC, claim 재시도 없음
- 조건별 전략당 예열 1라운드 후 측정 5라운드
- 라운드당 10개 burst, burst당 스레드 수만큼 요청
- 각 burst 전에 새 계정을 준비하고 시작 신호로 대기 중인 작업들을 동시에 해제
- 라운드마다 전략 순서를 반대로 하여 실행 순서 영향을 완화

총 측정 요청은 4,800개이며 별도로 예열 요청 960개가 실행됩니다.
이는 고정된 수의 작업을 동시에 실행하고 완료를 기다리는 closed-loop 실험입니다.
HTTP 부하 시험이나 운영 트래픽 재현이 아닙니다. 각 burst의 마지막 요청 완료 뒤
다음 데이터를 준비하므로 전체 실행 시간을 처리량 분모로 사용하지 않습니다.

## 수집 항목

`target/benchmarks/run-실행시각/` 폴더에 다음 파일이 생성됩니다.

- `environment.txt`: Java·OS·MySQL·격리 수준·풀 크기·반복 조건, 시작/완료 상태
- `samples.csv`: 요청별 전략·시나리오·결과 종류·서비스 호출 소요 시간
- `summary.csv`: 조건·라운드별 성공/거절 종류별 개수, 완료 요청/초, 성공 요청/초,
  전체 p50·p95·p99 및 성공/거절 요청 각각의 p95

응답 시간은 서비스 메서드 호출 직전부터 트랜잭션 종료 후 반환/예외까지입니다.
스레드 시작 대기와 데이터 준비는 제외되며 커넥션 대기와 잠금 대기는 포함됩니다.
처리량의 분모는 각 burst의 시작 신호 해제부터 모든 작업 완료 확인까지의 시간을 합산합니다.
분위수는 nearest-rank 방식이며 소수 표본의 p99는 최댓값에 가까울 수 있습니다.

## 정확성 검증과 실패 기준

측정 후 DB를 다시 읽고 각 계정의 실제 소유자가 성공 응답의 소유자와 같은지 확인합니다.
독립 계정 시나리오는 모든 요청 성공, 경쟁 시나리오는 burst당 하나만 성공해야 합니다.
예상 외 예외, 잠금 획득 실패, 타임아웃, 소유자 불일치는 벤치마크 실패입니다.
중도 실패한 실행의 부분 CSV를 완성 결과로 사용하지 않습니다.
완성 결과는 `environment.txt`의 마지막 `status=COMPLETED`와 Maven BUILD SUCCESS를 함께 확인합니다.

## 해석 원칙

빠르게 거절한 요청 때문에 처리량이 높아질 수 있으므로 성공 요청/초와 실패 종류를
함께 비교합니다. 낙관적 방식의 이미 사용됨 거절과 버전 충돌도 별도로 기록합니다.
같은 계정을 매 burst마다 새로 준비하여, 첫 요청 이후 영구히 사용된 계정만
반복 조회하는 편향을 피합니다. 잠금 구간에 인위적인 sleep은 넣지 않습니다.

5라운드의 중앙값과 범위를 먼저 비교합니다. 로컬 Docker 자원·JIT·GC·OS 스케줄링에
영향을 받으므로 작은 차이를 우열로 단정하지 않습니다. 장시간 안정성, 네트워크 지연,
HTTP 계층, 재시도 정책, 다중 서버 환경은 이번 측정 범위 밖입니다.
