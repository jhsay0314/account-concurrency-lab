## 성능 관측

각 값은 **5라운드별 지표의 중앙값**입니다. p95 열은 전체 표본을 합친 p95가 아니라
각 라운드 p95의 중앙값입니다. 처리량은 성공과 정상 거절을 포함한 완료 요청/초입니다.

독립 계정에서는 모든 요청이 성공합니다. 경쟁 조건은 burst당 한 건만 성공하므로
전체 완료 처리량을 발급 성공 처리량으로 표현하면 안 됩니다.
예를 들어 경쟁 16개 조건의 성공 요청/초 중앙값은 낙관적 29.818, 비관적 33.242입니다.
성공/거절 각각의 p95는 원시 요약 CSV에 별도로 기록했습니다.

## 일관성과 거절 방식

| 상황 | 전략 | 측정 요청 | 성공 | 이미 사용됨 | 버전 충돌 | 잠금 획득 실패 |
|---|---|---:|---:|---:|---:|---:|
| 독립 계정 (8·16 합계) | 낙관적 | 1,200 | 1,200 | 0 | 0 | 0 |
| 독립 계정 (8·16 합계) | 비관적 | 1,200 | 1,200 | 0 | 0 | 0 |
| 동일 계정 경쟁 (8·16 합계) | 낙관적 | 1,200 | 100 | 0 | 1,100 | 0 |
| 동일 계정 경쟁 (8·16 합계) | 비관적 | 1,200 | 100 | 1,100 | 0 | 0 |

각 burst마다 성공 개수와 DB에 저장된 소유자를 검증했고 모두 통과했습니다.
낙관적 방식은 갱신 시 버전 충돌로 패배한 요청을 거절했습니다.
비관적 방식은 잠금 대기 후 변경된 상태를 읽고 이미 사용된 계정으로 거절했습니다.
두 방식 모두 이번 실험에서 중복 성공이나 저장 소유자 불일치가 관측되지 않았습니다.

## 결론과 제한

이번 실행의 경쟁 조건에서는 비관적 방식의 완료 처리량 중앙값이 높았습니다.
그러나 독립 계정 16개 조건에서 비관적 처리량이 52.166–728.039로 크게 흔들렸고,
낙관적 방식도 편차가 컸습니다. 원인을 측정하지 않았으므로 JIT·GC·디스크·Docker 자원
중 특정 요인으로 단정할 수 없습니다. 따라서 일반적인 성능 우열이나 개선율을 주장하지 않습니다.

성공 요청 수가 다른 두 시나리오끼리도 처리량을 직접 비교하지 않습니다.
경쟁 조건의 대부분 요청은 갱신 성공이 아닌 거절로 끝납니다.
이는 서비스 계층의 짧은 burst 실험이며 HTTP 응답 시간, 장시간 부하 안정성,
재시도 포함 비용, 다중 서버의 운영 성능을 측정한 결과가 아닙니다.

다음 측정에서는 환경 부하를 통제하고 예열을 늘려 독립 프로세스로 재실행하며,
GC·CPU·디스크 지표를 함께 수집해 편차부터 조사하는 것이 적절합니다.

## 포트폴리오용 요약

가상의 계정 발급·재사용 서비스를 구현하고 MySQL에서 낙관적·비관적 잠금을 비교했다.
동시 요청 8·16개, 경쟁 유무별 5회 반복으로 4,800개 요청을 측정하고,
성공 요청과 저장된 소유자의 일치 여부를 검증했다. 두 전략의 거절 경로를
버전 충돌과 잠금 후 상태 확인으로 구분하고, 전체 완료 처리량과 성공 처리량을
분리해 분석했다. 성능 편차가 큰 조건은 우열 판단에서 제외했다.
